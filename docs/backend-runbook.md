# Backend runbook (Phase 4)

API Gateway HTTP API + Lambda, all in `ap-southeast-1`.

## Endpoints

| Method | Path | Auth | Status |
|---|---|---|---|
| GET | `/products` | public | live |
| GET | `/products/{slug}` | public | live |
| GET | `/courses` | public | live |
| POST | `/admin/sync-courses` | `x-admin-key` | live |
| POST | `/admin/retry-enrollment/{orderId}` | `x-admin-key` | 501 until Phase 6 |
| POST | `/webhooks/paymongo` | signature (Phase 6) | acknowledges only |

The PayMongo webhook returns **200, not 501**, before it is implemented.
PayMongo retries non-2xx deliveries and eventually disables the endpoint, so
acknowledging and logging is safer than accumulating failures. No money is
handled on that route yet, so acknowledging costs nothing.

## Deploying

```bash
cd infra && npx cdk deploy --require-approval never
```

Attach the custom domain once the ACM certificate is `ISSUED`:

```bash
cd infra && npx cdk deploy --require-approval never -c apiCertificateArn=arn:aws:acm:ap-southeast-1:651706741660:certificate/d38a7b18-6f23-4eee-a851-49a396581a00
```

The certificate ARN is passed as context rather than hardcoded so the stack stays
deployable while DNS validation is still pending — a pending record never blocks
backend work.

## Secrets

Read at runtime from Secrets Manager, cached per Lambda container. Nothing is
baked into the template or into environment variables.

| Secret | Used by |
|---|---|
| `hilom/supabase` | all catalog + order handlers |
| `hilom/moodle` | `sync-courses` |
| `hilom/paymongo/test` | webhook |
| `hilom/admin-api-key` | `/admin/*` (generated by CDK) |

Each function is granted read on only the secrets it needs.

### Getting the admin key

It is generated by CDK and never printed to the console or logs:

```bash
aws secretsmanager get-secret-value --region ap-southeast-1 --secret-id hilom/admin-api-key --query SecretString --output text
```

The key is read from Secrets Manager at request time rather than passed as a
Lambda environment variable, because env vars are visible to anyone with console
read access to the function — a wider audience than should hold an admin
credential. Comparison is constant-time.

This is a stopgap. Phase 7 moves `/admin/*` behind a Cognito admin group.

## Runtime note

Lambdas run **Node 24**, not Node 20 as the original plan specified. Node 20 was
deprecated on 2026-04-30 and new-function creation stops on 2027-02-01, so
starting on it would have meant inheriting a migration deadline.

## Moodle enrollment idempotency — confirmed

Calling `enrol_manual_enrol_users` twice for the same user + course neither
errors nor duplicates the enrollment. Verified against production with a
throwaway user and course 18 (`burger101`):

```bash
cd backend && MOODLE_WS_TOKEN=... npx tsx ../scripts/probe-moodle.ts --enrol-test <email> <courseId>
```

This is why the Phase 6 webhook can safely retry enrollment on a failure
without needing its own dedupe logic for the Moodle side — only the order
row's `paymongo_payment_id` uniqueness needs to guard against a duplicated
*payment* event; a duplicated *enrollment call* is already safe.

One transient finding along the way: production Moodle's DB connection
dropped mid-request once (`MySQL server has gone away`) during user creation.
The user was actually created despite the WS call reporting an error — worth
remembering that a `dmlreadexception` from Moodle doesn't guarantee the write
didn't happen, so a retry after such an error should check for an existing
record before creating another.
